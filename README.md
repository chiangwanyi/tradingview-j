# tradingview-j

旁路抓取**你本人已登录的 Chrome** 里 TradingView 图表页的 WebSocket 行情帧，
解出 **5 分钟 K 线**，按「一个标的一个文件夹、一天一个 CSV」落盘。

纯 Go 实现，**零第三方依赖**（含自写的 WebSocket 客户端），产物是一个 `tv-capture.exe`。
新版本里**没有任何 JavaScript** —— 之所以能做到，是因为程序只做被动监听，
不需要往页面里注入脚本，也不需要扩展。

## 工作流程

```
双击 tv-capture.exe
      │
      ├─ 读同目录的 config.json（没有就生成一份默认的）
      ├─ 等 Chrome 的调试端口出现      ← 没开就一直等，每 5 秒重试一次
      ├─ 等 TradingView 图表页出现     ← 没开就一直等，页面一出现自动接入
      │
      └─ 被动监听该页面的所有 WebSocket 帧
            │
            └─ 解析出 5 分钟 K 线 → 覆盖写 <数据目录>/<标的>/<日期>.csv
```

**你要做的只有一件**：在 Chrome 里随意拖动图表、或者用回放模式到处跳。
图表每走到一段没缓存的范围，页面自己就会向服务器要历史数据，程序把这段录下来。

程序**不会主动操作你的图表**（不拖动、不刷新、不注入脚本），
所以对 TradingView 而言没有任何"非人类"的交互序列。

## 前置条件：打开 Chrome 的远程调试开关

Chrome 136 起，给默认用户数据目录加 `--remote-debugging-port` 启动参数会被**静默忽略**，
端口根本不会开。所以"关掉 Chrome 再加参数重启"这条路走不通，只能用官方开关：

1. 打开你平时登录着 TradingView 的那个 Chrome
2. 地址栏访问 `chrome://inspect/#remote-debugging`
3. 勾选 **Allow remote debugging for this browser instance**
4. 保持 Chrome 开着，并打开 TradingView 的**图表页**（URL 里带 `/chart/`）

勾选后在**当前运行中的实例**上立即生效，不需要重启 Chrome、不需要重新登录。
代价是每次外部发起连接，Chrome 会弹一次授权框要求点 **Allow** —— 每个浏览器会话都要点一次。

程序启动后如果发现端口还没开，会打印这段操作步骤并每 5 秒重试一次，不用重启程序。

## 构建与运行

```bash
go build -o tv-capture.exe .     # 或者双击 build.cmd
./tv-capture.exe                 # 或者直接双击
```

停止：在窗口里按 `Ctrl+C`。程序会先把内存里的当天数据刷进 CSV 再退出。

## 配置：`config.json`

程序**不接受任何命令行参数**（因为这个 exe 的使用方式是双击，双击时传不进参数），
所有参数都在 exe 同目录的 `config.json` 里。文件不存在会自动生成一份默认的。

| 字段 | 默认值 | 说明 |
|---|---|---|
| `matchUrl` | `"tradingview.com/chart"` | 挂到哪个标签页上：按 URL/标题子串匹配。同时开多个图表页会全部挂上 |
| `symbol` | `""` | 强制指定标的。留空则自动识别（推荐留空） |
| `cdpPort` | `0` | `0` = 自动发现（读 `DevToolsActivePort`，再探测 9222/9229/9333） |
| `intervalSeconds` | `300` | **只收这个周期**的 K 线。目前按需求只考虑 5 分钟 |
| `outDir` | `"data"` | K 线 CSV 的根目录，结构见下 |
| `rawDir` | `"raw"` | 原始帧留档的根目录 |
| `saveRawFrames` | `true` | 是否留档原始 WebSocket 帧（复盘协议用，占磁盘） |
| `csvHeader` | `true` | CSV 是否写表头行 |
| `flushSeconds` | `1` | CSV 落盘间隔。内存里攒着，按这个间隔整体重写 |
| `attachPollSeconds` | `3` | 多久检查一次新出现的图表页 |
| `retrySeconds` | `5` | 接入失败后的重试间隔 |
| `statusSeconds` | `15` | 状态行刷新间隔 |
| `networkBufferMB` | `200` | CDP 网络事件缓冲上限 |
| `maxFrameMB` | `16` | 单帧上限，超了断开重连（防止畸形长度头把内存吃光） |
| `pauseOnExit` | `true` | 出错退出时是否等回车（双击运行时能看清报错） |

相对路径（`outDir` / `rawDir`）都相对 **exe 所在目录**展开，而不是当前工作目录 ——
双击运行时工作目录不可靠。

## 数据长什么样

```
data/                                ← outDir
  _symbols.json                      程序自己维护的「标的名 → 文件夹」索引
  CME_MINI_MNQ1!/                    ← 一个标的一个文件夹
    2026-10-15.csv                   ← 文件名就是日期
    2026-10-16.csv
  BINANCE_BTCUSDT/
    2026-10-16.csv
raw/                                 ← rawDir（saveRawFrames 打开时才有）
  CME_MINI_MNQ1!/
    2026-10-16T09-30-00.ndjson       一行一条原始帧，事后可复盘协议
```

`2026-10-16.csv` 的内容：

```csv
time,open,high,low,close,volume
2026-10-16 09:40,30067.25,30067.25,30056,30061.5,847
2026-10-16 09:45,30061.5,30080,30055.25,30072.5,1024
```

- **时间列是明文** `yyyy-MM-dd HH:MM`（这根 K 线的**开盘时间**），不是 Unix 秒。
  用 Excel 或文本编辑器打开就能读懂，不需要再换算。
- **时区用本机时区**（`time.Local`）。启动横幅里会明确打印当前用的是哪个时区。
  这也是文件名里"哪一天"的依据 —— 换机器/换时区跑，同一根 K 线的归属日会跟着变，
  所以尽量固定在同一台机器上采集。
- 成交量缺失时该列留空，不会因此丢整行。

### 写入语义：整体重写，不做「是否已存在」判断

需求里明确写了"写入是直接覆盖，不考虑是否已经存在相同的时间的数据"，实现方式是这样的：

- 内存里按 `(标的, 日期)` 维护一份 `时间戳 → K线` 的映射；
- 同一个时间戳再来就是**直接覆盖**（正在走的那根 K 线会被 `du` 增量反复推送，这是常态）；
- 每 `flushSeconds` 秒把脏掉的日文件**整体重写**一遍（先写 `.tmp` 再 rename，原子替换）。

所以**重复数据在结构上不可能出现**，不需要去查"这根是不是已经有了"。
一天只有 288 行（5 分钟级别，一天最多 288 根），整体重写的成本可以忽略。

程序**启动时会把磁盘上已有的当日文件读回内存**再合并 —— 不读的话，
重启后接着拖同一个日期就会把之前抓的那部分覆盖掉。

## 关键设计

### 周期怎么认定：靠相邻时间戳的众数差反推

帧里**没有任何字段直接写着周期**。唯一看起来像的 `lbs.bar_close_time` 是个陷阱：
它挂在 series 容器上，整段抓包里只有一个取值（图表右侧可视边界），
拿它减开盘时间会得到随时间线性漂移的垃圾值。这一点是被数据推翻的，不是推断的。

所以周期只能反推：同一批 K 线内部相邻时间戳的差、以及跨批次的差，取**众数**。
`timescale_update` 一次回来 300 根，绝大多数相邻差都是 300 秒（中间夹着交易所休市造成的
一两个大间隔），众数立刻确定 —— 这也是"众数"而不是"平均值/最小值"的原因。

**反推出来之前，这批 K 线先暂存不落盘。** 宁可晚几百毫秒，
也不要把 1 小时图的 K 线混进 5 分钟目录里 —— 那种污染事后几乎发现不了。
一旦确认某个序列的周期不是 `intervalSeconds`，该序列的数据会被**整段跳过**并在日志里说明原因。

### 标的名怎么认定：只认 `symbol_resolved`，按「会话 + 序列」归属

先说一个踩过的坑：**同一个页面的 WebSocket 上跑的不只是图表数据。**
侧边栏 / 自选 / 报价面板的消息（`qsd`）里同样带 `pro_name`，而且是**别的品种**。
实测后果：在 `CME_MINI:MNQ1!` 的 5 分钟图上抓来的 K 线被写进了 `data/NASDAQ_NDX/` ——
一条自选里的纳指报价就足以把图表品种改掉：

```json
{"m":"qsd","p":["qs_multiplexer_full_UZqj66fHTjYn",
                {"n":"NASDAQ:NDX","s":"ok","v":{"subsession_id":"regular",
                 "pro_name":"NASDAQ:NDX","typespecs":["main","synthetic"]}}]}
```

（顺带一提：`CME_MINI:MNQ1!` 自己的报价里还夹着 `"underlying-symbol":"NASDAQ:NDX"`
—— 微纳指本来就跟踪 NDX。所以「在文本里找 NDX」这种做法也早晚会错。）
**结论：品种只能从 `symbol_resolved` 里认，别在整帧里搜 `pro_name`。**

现在的做法是认协议语义，把「谁是谁」按会话拆开：

| 消息 | 方向 | 给出什么 |
|---|---|---|
| `{"m":"symbol_resolved","p":["cs_xxx","sds_sym_1",{"pro_name":"CME_MINI:MNQ1!",…}]}` | recv | 品种键 → 品种名 |
| `{"m":"create_series","p":["cs_xxx","sds_1","s1","sds_sym_1","5",300,""]}` | send | 序列键 → 品种键 |
| `{"m":"timescale_update"}` / `{"m":"du"}`，p[0] 是会话、p[1] 里是 `{"sds_1":{"s":[…]}}` | recv | 会话 + 序列键（以及 K 线） |

一根 K 线的归属 = 它所在消息的**会话** + 它所属的**序列名** → 品种键 → 品种名。判定顺序：

1. `config.json` 里的 `symbol`（填了就以此为准，连帧都不看）
2. 这根序列被 `create_series` 绑到了某个品种键，而该品种键被 `symbol_resolved` 解析过（最精确）
3. 这个会话只解析出一个品种 —— 那只能是它
4. 整个页面只解析出一个品种 —— 大概率是它（页面刷新、旧会话残留等场景靠这条兜住）
5. 什么都没有时，用页面 URL 的 `?symbol=` **猜**一个，并在日志里说明这是猜的

上面 2/3/4 都给不出结论时，K 线**先攒着不落盘**，等品种明确后一次性补写 ——
不知道写进哪个文件夹，硬写就会污染别的标的。同一个会话里解析出多个品种（多面板、对比图）时，
只有第 2 条能给出精确答案，其余情况一律暂存不猜。

页面上出现的**别的**品种会被记下来并提示一次：

```
目前看到页面上另有 8 个品种在走报价（BINANCE:BTCUSDT.P、…）—— 它们不是图表品种，不参与归属判定
```

收工汇总里也会列出完整名单（按被报价的频率排序）。这条日志就是用来一眼确认
「品种认得对不对、目录名该不该是它」的。

> 老版本 Node 实现里有一句注释说"抓包里没有 `symbol_resolved`"，实测**是有的**，
> 而且它才是一切的依据。
> `modify_series`（图表上换品种时可能用到的信令）在这次抓包里没出现过，代码按与
> `create_series` 相同的参数顺序试着解析 —— **这一条是推断**；形状对不上时会拒绝解析，
> 退化成「按会话判定」而不是乱配。

### 周期反推也按「会话 + 序列」分开

一个页面上可能同时存在多个图表会话（刷新前的旧会话、多面板布局的各面板、页面上的迷你图），
它们各自的序列**都叫 `sds_1`**。周期投票如果按序列名全局汇总，两个会话会互相污染：
1 小时图的会话可能被 5 分钟会话的多数票放行，那就等于直接写进 5 分钟目录。

代价是：某个会话只零星推了一两根、周期再也反推不出来时，那几根会一直停在暂存里
（状态行里 `暂存 N 根` 能看见，收工汇总也会报）。这是刻意的 —— 宁可留着，也不赌。

### 为什么只做被动监听

主动拖动图表会让你在 TradingView 上的交互序列变得不像人操作的，高频使用有被风控的可能。
这一版因此**完全没有自动回拉功能**：不拖动、不刷新、不注入脚本，页面干什么就录什么。
想填历史就自己在图表上往回拖，或直接用回放模式跳日期 —— 效果一样，但风险低得多。

低频、小批量自用风险可控；**不要高频批量拉，不要全品种刷。**

### 为什么是 Go、为什么零依赖

- 需求要求整体 Go 化，产物是单个 exe（不需要装运行时）。
- 唯一需要的外部能力是"一个 WebSocket 客户端"，而这部分可以完全用标准库实现
  （`net` + `crypto/tls` + `crypto/sha1` + `encoding/base64`），
  于是整个项目没有任何 `require`，`go.mod` 干净得像一张纸。
- 自写的客户端必须处理两件被真实数据逼出来的事：**单帧可达 247KB**（要支持 64 位长度
  与分片重组），以及**掩码方向不能搞反**（搞反了 Chrome 直接按协议错误断开，
  而且报错信息不会告诉你原因）。

### 时间轴与覆盖度报告：这一版没有

旧版有日历热力图和覆盖度报告。这一版按需求做了减法：
没有网页界面、没有自动回拉、没有覆盖度分析。数据现在是**明文 CSV**，
想统计"哪几天缺哪段"，用 Excel、Python 或者几行 shell 都比内置一个报告模块更灵活。

## 测试

### 自动测试：全部离线，不启动任何浏览器

```bash
go test ./...
```

这一点是硬要求：**禁止用无头浏览器测试**（慢，而且浏览器进程中断这类问题在测试里看不见）。
替代方案是**用一个假 CDP 服务端扮演 Chrome** —— 它能应答 `Target.getTargets` /
`Target.attachToTarget` / `Network.enable`，然后把**真实抓包**当成 WebSocket 帧事件推下去：

```
internal/capture/capture_test.go
  ├─ 起一个假 CDP 服务端（HTTP /json/version + WebSocket 命令循环）
  ├─ 推 3 条真实帧（symbol_resolved / timescale_update / du 各一条，外加一条心跳）
  └─ 断言：CSV 真的写出来了、300 行、时间是明文、表头正确、
           原始帧留档存在、日志里确认了品种与周期
```

除了"Chrome 自己的行为"以外，从握手、分帧、抽 K 线、周期判定、品种识别到落盘、留档，
全部真跑了一遍。各层另有单元测试：

```bash
go test ./internal/tvproto/   # 分帧 / 抽 K 线 / 品种与序列绑定解析（含两份真实抓包回归）
go test ./internal/store/     # CSV 落盘 / 覆盖语义 / 重启后合并 / 坏行容错
go test ./internal/ingest/    # 周期反推 / 暂存补写 / 品种归属与串味防护
go test ./internal/cdp/       # 端点发现 / 命令与事件 / 超时 / 断线
go test ./internal/wsclient/  # 握手 / 大帧 / 分片 / ping-pong
go test ./internal/config/    # 配置生成 / 缺键补齐 / 非法值回退
go test ./internal/logx/      # 状态行原地刷新 / 中文按显示宽度擦除 / 重定向不留回车
```

回归样本有两份，都是从真实抓包里裁出来的：

**`testdata/real-capture.ndjson`**（2026-10-16，`CME_MINI:MNQ1!` 5 分钟图）：
meta + 一条携带完整 300 根历史的 `timescale_update` + 一条 `du` + 一条心跳。
里面的期望值是用独立脚本统计出来的，**不是照抄被测代码的输出** ——
用被测代码生成期望值等于没测。
注意它里面有两个图表会话：那条 `du` 属于另一个会话（`cs_gaSTXIAFy41H`）且只有 1 根，
凑不齐两票，所以按规则一直暂存 —— 这正是「周期按会话分别反推」被钉住的地方。

**`testdata/mixed-symbols.ndjson`**：这次「品种认错」的回归样本。同一个页面上开着
`CME_MINI:MNQ1!` 的 5 分钟图，同时有 10 个别的品种在走报价（`NASDAQ:NDX` 被报价 5 次，
就是它把旧版本带跑偏的）。样本里有 `resolve_symbol` / `create_series` / `symbol_resolved`、
一条 300 根的 `timescale_update`、三条 `du`（有两条落在 NASDAQ:NDX 那条报价**之后**，
正是旧版本会写错目录的那几根），以及那条带 `pro_name` 的 NDX 报价。它锁住三件事：

1. 全部 K 线来自图表会话的 `sds_1`（300 个不同时间戳，独立脚本统计的值）；
2. 那条 NDX 报价**一根 K 线都不贡献**，也改不了图表品种；
3. 跑完整链路（假 CDP 服务端 → CSV）之后，数据目录里**只有一个**标的文件夹。

顺带把「按形状抽 K 线会不会误抽报价/指标」这件事用整段真实抓包验过了：
那次抓包的 655 帧里，能抽出 K 线的段共 211 个，**全部**是图表会话的 `du` / `timescale_update`，
`qsd`（含 57KB 的纳指报价）与 `st` 指标一根都没贡献。

### 人工联调：必须由你自己打开浏览器

自动测试覆盖不到"Chrome 的真实行为"，这一段只能人工做，步骤很短：

1. 打开 Chrome → `chrome://inspect/#remote-debugging` → 勾选 Allow remote debugging
2. 打开 TradingView 的图表页，切到 **5 分钟**周期
3. 双击 `tv-capture.exe`
4. 观察窗口输出，应当依次出现：
   - `发现浏览器调试端点：port 9222 · 来源 DevToolsActivePort`
   - `CDP 通道已建立，开始等待 TradingView 图表页…`
   - Chrome 里点一次 **Allow**
   - `已接入图表页：…`（附带识别到的品种）
   - `[状态] 页[...] 帧 N(收N/发N) …` 这行会原地刷新
5. 在图表上**往回拖动**几次，或用回放模式跳几个日期
6. 到 `<数据目录>/<标的>/<今天>.csv` 看文件是否在长大
7. `Ctrl+C` 退出，确认最后打印出"落盘完成"和本次写入统计

排查要点：

| 现象 | 原因 |
|---|---|
| 一直打印"还没发现 Chrome 调试端点" | 第 1 步的开关没勾，或 Chrome 没开 |
| 连上了但没弹 Allow 框、随后报"连接已关闭" | 上一次的授权被拒了，重新连一次并在浏览器里点 Allow |
| 找到页面但提示"接不进这个页面" | **该标签页上开着开发者工具** —— 一个标签页同时只能有一个调试会话，关掉 DevTools 即可 |
| 帧在涨但 CSV 不涨 | 图表周期不是 5 分钟（日志里会写"序列 xxx 的周期是 1h"），或状态行里 `周期` 显示"未定" |
| 状态行里 `暂存 N 根` 一直不降 | 那些 K 线所在的序列凑不齐两票、周期反推不出来（一般是页面上另一个会话/迷你图的零星数据），或者它们的会话里解析出多个品种而序列没有绑定。**它们不会落盘，也不影响主图采集** —— 这是刻意的 |
| `品种` 显示的标的跟你正在看的图表不一致 | 先看日志里那句 `识别品种：…（会话 … · 品种键 …）` 对不对。实在不放心就把 `config.json` 的 `symbol` 填死 |
| CSV 文件被 Excel 占用导致写失败 | 日志会提示"下个周期重试"，关掉 Excel 即可 |

## 目录结构

```
main.go                 入口：横幅、配置、信号处理、退出汇总
internal/config/        config.json 的加载 / 生成 / 校验
internal/cdp/           CDP 接入：端点发现、命令与事件、目标页挑选
internal/wsclient/      极简 WebSocket 客户端（零依赖，支持大帧与分片）
internal/tvproto/       协议层：~m~/~h~ 分帧、按形状抽 K 线、标的解析
internal/ingest/        解码器：周期反推、暂存、交给落盘出口
internal/store/         CSV 存储：标的文件夹 + 每日文件整体重写
internal/rawlog/        原始帧留档（NDJSON）
internal/capture/       常驻会话：等端口、等页面、挂监听、状态行
internal/logx/          控制台日志（UTF-8 代码页、状态行原地刷新）
internal/wstest/        测试专用的手写 WebSocket 服务端（不进最终产物）
testdata/               真实抓包裁剪出的回归样本
legacy/                 旧版 Node 实现（src/ server/ web/ bin/ test/ + 旧 data），只作留档
```

## 与旧版的关系

`legacy/` 里是重构前的 Node 实现（网页工作台 + SQLite + 自动回拉 + 覆盖度报告）。
它现在只是一个参照物：**旧库文件与旧抓包都原样躺在 `legacy/data/` 下，没有删**。
确认不需要之后，直接删掉整个 `legacy/` 目录即可。

需要注意的具体差异：

| | 旧版（legacy/） | 现在 |
|---|---|---|
| 界面 | 本地网页工作台（三页签） | 无界面，纯命令行 |
| 存储 | 一个标的一个 SQLite | 一个标的一个文件夹，一天一个 CSV |
| 时间 | Unix 秒 | 明文 `yyyy-MM-dd HH:MM` |
| 配置 | 命令行参数 + 网页表单 | 只有 `config.json` |
| 主动回拉 | 有（默认关闭） | 去掉 |
| 覆盖度报告 | 有 | 去掉 |
| 测试 | 三层，含无头浏览器 e2e | 全离线，用假 CDP 服务端替代浏览器 |
| 运行时 | Node 22 | 一个 exe |

## 注意

抓取属于对 TradingView 服务条款的灰色操作。低频、小批量自用风险可控；
**不要高频批量拉，不要全品种刷。**

这一版只做被动监听，是刻意的：不产生任何主动交互，也就不给风控提供触发依据。
但也不要长时间挂着让它连续录几十个小时 —— 需要哪段历史，开一次拖一遍就够了。
