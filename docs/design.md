## 为什么只做被动监听

主动拖动图表会让你在 TradingView 上的交互序列变得不像人操作的，高频使用有被风控的可能。
这一版因此**完全没有自动回拉功能**：不拖动、不刷新、不注入脚本，页面干什么就录什么。
想填历史就自己在图表上往回拖，或直接用回放模式跳日期 —— 效果一样，但风险低得多。

同理，程序不接受命令行参数、不做批量调度、没有定时任务：
**低频、小批量自用风险可控，不要高频批量拉，不要全品种刷。**

这条约束还带来一个意外的好处：既然不注入脚本，就不需要浏览器扩展，
也就**没有任何 JavaScript**要维护 —— 「必须保留的 JS」是零。

## 为什么是 Go、为什么零依赖

- 需求要求整体 Go 化，产物是单个 exe（不需要装运行时，拷到哪都能跑）。
- 唯一需要的外部能力是「一个 WebSocket 客户端」，而这部分可以完全用标准库实现
  （`net` + `crypto/tls` + `crypto/sha1` + `encoding/base64`），
  于是整个项目没有任何 `require`，`go.mod` 干净得像一张纸。
- 自写的客户端必须处理两件被真实数据逼出来的事：**单帧可达 247KB**（要支持 64 位长度
  与分片重组），以及**掩码方向不能搞反**（搞反了 Chrome 直接按协议错误断开，
  而且报错信息不会告诉你原因）。

## 标的名怎么认定：只认 `symbol_resolved`，按「会话 + 序列」归属

先说一个踩过的坑：**同一个页面的 WebSocket 上跑的不只是图表数据。**
侧边栏 / 自选 / 报价面板的消息（`qsd`）里同样带 `pro_name`，而且是**别的品种**。
实测后果：在 `CME_MINI:MNQ1!` 的 5 分钟图上抓来的 K 线被写进了 `data/NASDAQ_NDX/` ——
一条自选里的纳指报价就足以把图表品种改掉：

```json
{"m":"qsd","p":["qs_multiplexer_full_Uzqj66fHTjYn",
                {"n":"NASDAQ:NDX","s":"ok","v":{"subsession_id":"regular",
                 "pro_name":"NASDAQ:NDX","typespecs":["main","synthetic"]}}]}
```

（顺带一提：`CME_MINI:MNQ1!` 自己的报价里还夹着 `"underlying-symbol":"NASDAQ:NDX"`
—— 微纳指本来就跟踪 NDX。所以「在文本里找 NDX」这种做法也早晚会错。）

**结论：品种只能从 `symbol_resolved` 里认，别在整帧里搜 `pro_name`。**

现在改为认协议语义，把「谁是谁」按会话拆开：

| 消息 | 方向 | 给出什么 |
|---|---|---|
| `{"m":"symbol_resolved","p":["cs_xxx","sds_sym_1",{"pro_name":"CME_MINI:MNQ1!",…}]}` | recv | 品种键 → 品种名 |
| `{"m":"create_series","p":["cs_xxx","sds_1","s1","sds_sym_1","5",300,""]}` | send | 序列键 → 品种键 |
| `{"m":"timescale_update"}` / `{"m":"du"}`，p[0] 是会话、p[1] 里是 `{"sds_1":{"s":[…]}}` | recv | 会话 + 序列键（以及 K 线） |

一根 K 线的归属 = 它所在消息的**会话** + 它所属的**序列名** → 品种键 → 品种名。判定顺序：

1. `config.json` 里的 `symbol`（填了就以此为准，连帧都不看）
2. 这根序列被 `create_series` 绑到了某个品种键，而该品种键被 `symbol_resolved` 解析过（最精确）
3. 这个会话只解析出一个品种 —— 那只能是它
4. 整个页面只解析出一个品种 —— 大概率是它（页面刷新、旧会话残留等场景靠这条兜住）
5. 什么都没有时，用页面 URL 的 `?symbol=` **猜**一个，并在日志里说明这是猜的

上面 2/3/4 都给不出结论时，K 线**先攒着不落盘**，等品种明确后一次性补写 ——
不知道写进哪个文件夹，硬写就会污染别的标的。同一个会话里解析出多个品种（多面板、对比图）时，
只有第 2 条能给出精确答案，其余情况一律暂存不猜。

页面上出现的**别的**品种会被记下来并提示一次，收工汇总里也会列出完整名单（按被报价的频率排序）：

```
目前看到页面上另有 8 个品种在走报价（BINANCE:BTCUSDT.P、…）—— 它们不是图表品种，不参与归属判定
```

这条日志就是用来一眼确认「品种认得对不对、目录名该不该是它」的。

> 老版本 Node 实现里有一句注释说「抓包里没有 `symbol_resolved`」，实测**是有的**，
> 而且它才是一切的依据。
> `modify_series`（图表上换品种时可能用到的信令）在这次抓包里没出现过，代码按与
> `create_series` 相同的参数顺序试着解析 —— **这一条是推断**；形状对不上时会拒绝解析，
> 退化成「按会话判定」而不是乱配。

## 周期怎么认定：靠相邻时间戳的众数差反推

帧里**没有任何字段直接写着周期**。唯一看起来像的 `lbs.bar_close_time` 是个陷阱：
它挂在 series 容器上，整段抓包里只有一个取值（图表右侧可视边界），
拿它减开盘时间会得到随时间线性漂移的垃圾值。这一点是被数据推翻的，不是推断的。

所以周期只能反推：同一批 K 线内部相邻时间戳的差、以及跨批次的差，取**众数**。
`timescale_update` 一次回来 300 根，绝大多数相邻差都是 300 秒（中间夹着交易所休市造成的
一两个大间隔），众数立刻确定 —— 这也是「众数」而不是「平均值/最小值」的原因。

**反推出来之前，这批 K 线先暂存不落盘。** 宁可晚几百毫秒，
也不要把 1 小时图的 K 线混进 5 分钟目录里 —— 那种污染事后几乎发现不了。
一旦确认某个序列的周期不是 `intervalSeconds`，该序列的数据会被**整段跳过**并在日志里说明原因。

顺带说明 `intervalSeconds` 的定位：它不是「告诉程序该收什么周期」，
而是「**允许**哪个周期落盘」的闸门。实际周期永远从数据里反推。

## 周期反推也按「会话 + 序列」分开

一个页面上可能同时存在多个图表会话（刷新前的旧会话、多面板布局的各面板、页面上的迷你图），
它们各自的序列**都叫 `sds_1`**。周期投票如果按序列名全局汇总，两个会话会互相污染：
1 小时图的会话可能被 5 分钟会话的多数票放行，那就等于直接写进 5 分钟目录。

所以投票按 `seriesKey{scope, name}` 分别做。代价是：某个会话只零星推了一两根、
周期再也反推不出来时，那几根会一直停在暂存里（状态行里 `暂存 N 根` 能看见，
收工汇总也会报）。这是刻意的 —— 宁可留着，也不赌。

## CSV 写入语义：整体重写，不做「是否已存在」判断

需求里明确写了「写入是直接覆盖，不考虑是否已经存在相同的时间的数据」，实现方式是这样的：

- 内存里按 `(标的, 日期)` 维护一份 `时间戳 → K线` 的映射；
- 同一个时间戳再来就是**直接覆盖**（正在走的那根 K 线会被 `du` 增量反复推送，这是常态）；
- 每 `flushSeconds` 秒把脏掉的日文件**整体重写**一遍（先写 `.tmp` 再 rename，原子替换）。

所以**重复数据在结构上不可能出现**，不需要去查「这根是不是已经有了」。
一天只有 288 行（5 分钟级别，一天最多 288 根），整体重写的成本可以忽略。

程序**启动时会把磁盘上已有的当日文件读回内存**再合并 —— 不读的话，
重启后接着拖同一个日期就会把之前抓的那部分覆盖掉。

被 Excel 打开着的文件在 Windows 上 rename 会失败，这时该日文件保持「脏」状态，
下个周期重试；日志会提示，不会丢数据。

### 由此推出的一个报警口径

既然写入是「整体重写 + 原子改名」，**同一时间戳在文件里出现两次在结构上不可能**。
所以菜单选项 2 里那个 `重复N行` 备注是有效报警（历史原因：早先想用「时间戳是否落在
文件名日期之外」来做时区变更报警，写完发现它恒为 0 —— CSV 里存的是明文本地时间，
读回来用任何时区解析，日期部分都还是原文那一天，判据自己是循环的。永远不响的检查比没有检查更糟，
已删除）。

## 报告能力的边界

早先的 Node 版有日历热力图和覆盖度报告（还有整套网页界面）。现在按需求做了减法：
没有网页界面、没有自动回拉，只保留菜单选项 2 的一次只读扫描，
回答「每个标的每天多少根、缺在哪」。

更细的仍然没有：日历热力图、把缺口区间一条条列出来、跨标的联动对比。
数据本身就是明文 CSV，这些用 Excel / Python 几行就能切，内置一个报告模块反而更难改。

统计口径刻意**复用落盘时的同一份解析代码**（`store.readDayFile` / `parseRow` / `readIndexFile`）。
两边各写一份解析，迟早会出现「文件里 288 行、分析说 287 根」这种没法判断该信谁的情况。
同理，分析走的是纯只读的 `store.Scan`，而不是写入用的 `store.Store`（后者一 Open 就会建目录、
会往 `_symbols.json` 里分配标的目录名）—— **统计动作不该对数据产生任何副作用**。

## 附录：协议与实测事实

以下都是实测出来的（括号里注明来源），不是从文档或推测得来的。改协议层之前请先读完。

### 帧格式

- 帧是 `~m~<长度>~m~<负载>`；心跳有两种形态都见过 —— 裸 `~h~1` 与 `~m~4~m~~h~1`。
  第二种如果不单独识别，就会被当成「无法解析的 JSON」，心跳计数也会跟着丢。
- **声明长度与实测不符约 3%**（5305 段中 146 段）→ 对不上时必须退化为「切到下一个帧头之前」；
  **但「负载长度必须等于声明长度」这一条不能省**，否则声明超长时会把后面几段一起吞掉。
- 单帧最大实测 **247KB** → WS 客户端必须支持 64 位长度与分片重组；写帧必须掩码。
- K 线形状是 `{s:[{i,v:[t,o,h,l,c,v]}]}`，`t` 是 Unix 秒，series 名是它上一层的键名（`sds_1`…）。
  `st1`/`st2` 是指标（挂在 `st` 键下）、`qsd` 是报价，都不会被误抽。

### 按形状抽 K 线会不会误抽报价 / 指标

不会。用整段真实抓包（655 帧）验过：能抽出 K 线的段共 **211 个，全部**是图表会话的
`du` / `timescale_update`；`qsd`（含那条 57KB 的纳指报价）与 `st` 指标**一根都没贡献**。

### 报价里的伪品种键

形如 `={"adjustment":"splits",…,"symbol":"CME_MINI_DL:MNQ1!"}` ——
**它不是品种名**，别拿它当目录名。

### 图表取数与休市

- 图表**按需**取数：可视范围走出缓存窗口才发 `request_more_data` →
  所以「拖图表」就是填历史的手段，程序自己不会去要数据。
- CME 期货休市（UTC）：每日 21:00–22:00 结算，周六全天 + 周日 22:00 前。
  这解释了数据里那些看起来像缺口的洞：工作日日文件 276 根 / 缺口 12 / 最大断档 1时5分，
  周六日文件约 60 根（凌晨收市）。**都是正常形态，不是丢数据。**
- `lbs.bar_close_time` **不是**收盘时间，是图表右侧可视边界（见「周期怎么认定」）。

### Chrome 侧的行为

- Chrome ≥ 136：给默认用户数据目录加 `--remote-debugging-port` 被**静默忽略**，
  只能走 `chrome://inspect/#remote-debugging` 的开关；每个浏览器会话要重勾，
  每次外部连接会弹一次 Allow 框，**不点就不通**。
- 新版 Chrome 只开放**浏览器级 WS**：`/json/version`、`/json/list` 一律 404。
  端口与 WS 路径从 `<User Data>/DevToolsActivePort` 读（第一行端口，
  第二行 `/devtools/browser/<uuid>`）。页面发现走 `Target.getTargets` +
  `Target.attachToTarget`(flatten)。
- **一个标签页同时只能有一个调试会话** → 该页开着 DevTools 时 attach 必失败
  （代码退避 1 分钟后重试）。

## 文件命名与目录分配

- 标的 → 文件夹只做文件系统需要的最小替换（`<>:"/\|?*` 与控制字符换成 `_`），
  不做拼音/转写：`CME_MINI:MNQ1!` → `CME_MINI_MNQ1!`。
- 撞名（大小写归一后相同、或 slug 化后相同）时**追加短哈希**，绝不「猜一个相近的名字」——
  那会让两个标的的数据混进同一个目录。映射关系记在 `_symbols.json`，
  没有索引时先把磁盘上已有的目录认领成「标的名 = 目录名」。
- 读写时间列都用**本机时区**（`time.Local`），文件名 `yyyy-MM-dd.csv` 就是这个时区下的日期。
  换机器/换时区跑，同一根 K 线的归属日会跟着变。

## 历史：旧版 Node 实现

重构前是一个 Node 22 的实现（本地网页工作台 + 每个标的一个 SQLite + 可选的自动回拉 +
覆盖度报告 + 含无头浏览器的三层测试）。它在 2026-10-16 被**整体删除**了
（`legacy/` 目录，60 个文件，含旧库文件与旧抓包）；要从 git 历史里取回：

```bash
git checkout ac9e35c -- legacy/     # ac9e35c = 删除前的最后一个提交
```

保留这份对照表，是因为下面每一条差异都对应一个刻意的决定：

| | 旧版（Node） | 现在 |
|---|---|---|
| 界面 | 本地网页工作台（三页签） | 无界面，菜单式命令行 |
| 存储 | 一个标的一个 SQLite | 一个标的一个文件夹，一天一个 CSV |
| 时间 | Unix 秒 | 明文 `yyyy-MM-dd HH:MM` |
| 配置 | 命令行参数 + 网页表单 | 只有 `config.json` |
| 主动回拉 | 有（默认关闭） | 去掉（风控优先） |
| 覆盖度报告 | 有（日历热力图） | 只保留按天的只读统计 |
| 测试 | 三层，含无头浏览器 e2e | 全离线，用假 CDP 服务端替代浏览器 |
| 运行时 | Node 22 | 一个 exe |
